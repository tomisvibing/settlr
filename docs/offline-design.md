# Offline support: design

Status: proposal, nothing built. Roadmap item: "Offline support: open the app and queue entries without signal".

## What people actually need

The moment that matters is **adding an expense somewhere with bad signal** (a restaurant basement, a plane, roaming abroad), then having it show up for the group later. Everything else offline is a nice-to-have. So the goal is:

1. The app opens with no signal and shows the last data it saw.
2. Adding an expense works offline, shows up immediately on this device marked as waiting, and syncs when the connection is back.
3. Nothing is ever silently lost or duplicated.

Not goals for the first version: editing or deleting offline, creating groups offline, offline sign-in, or two people editing the same entry offline (see "Out of scope").

## How the app works today

These facts shape the design:

- **Nothing is cached.** `public/sw.js` only handles push notifications and says so ("it doesn't cache anything, so the app always loads fresh"). With no signal the app doesn't open at all.
- **All data loads in one go.** `loadAllData()` in `src/data.js` reads eight tables in parallel and rebuilds `state`. There is no local copy that survives a reload.
- **Writes go straight to Supabase from the browser**, and one user action is often several statements. Saving an expense (`saveExpenseRow` in `src/dialogs/expense.js`) inserts the `expenses` row, *then* inserts its `expense_splits`. If the connection drops between the two, the expense exists with no splits. That already matters online, and it matters much more for a queue that retries.
- **Live updates** (`src/live.js`) reload everything when any table changes, and again after a dropped realtime connection reconnects.
- **IDs are generated by the database** (`gen_random_uuid()`), so the client can't name a row before it exists.
- **Exchange rates are fetched** when an expense is in another currency (`src/rates.js`), which fails offline.
- **Receipts upload first** to Storage, and the expense stores the path.

## Proposed design

Three layers, each shippable on its own.

### Layer 1: app shell cache (opens offline)

Precache the built files in the service worker so the app loads without a network.

- Vite already emits hashed filenames, so the precache list can be generated at build time (a small Vite plugin or `vite-plugin-pwa` in `generateSW` mode) and versioned by the build.
- Strategy: cache-first for the hashed assets, network-first with a cache fallback for `index.html`. A new deploy then reaches people on their next online load. Show a "New version available, reload" toast rather than swapping the page under someone.
- Keep the existing push handlers. `skipWaiting` and `clients.claim` are already there.
- Risk: a bad deploy that gets cached. Mitigation: `index.html` stays network-first, and the worker can be rolled back by shipping a new one. Add a kill switch (the worker unregisters itself if a `/sw-off` file exists).

### Layer 2: read cache (shows the last data)

Persist the last successful `loadAllData()` result and use it when a load fails because there's no network.

- Store in **IndexedDB** (not `localStorage`, which is synchronous and small). One record per signed-in user ID, holding the raw rows `loadAllData` already fetches plus a timestamp. Rebuilding `state` from the cache reuses the existing reshaping code; the cache sits *before* that code, not after.
- On load: try the network; on failure, fall back to the cache and show a banner, "Offline. Showing what settlr last saw, 2h ago."
- While showing cached data, writes other than "add expense" are disabled with a short reason.
- **Privacy:** this puts names, balances and expense descriptions on the device at rest, unencrypted. Clear it on sign-out and on account deletion, and scope it by user ID so a shared device can't show someone else's data. Say so in the docs.

### Layer 3: write queue for adding expenses

This is the hard part.

**Make the write atomic and idempotent first.** Add a database function, for example `add_expense(expense jsonb, splits jsonb)`, that inserts the expense and its splits in one transaction. The client supplies the expense's `id` (a UUID made on the device), and the function does nothing if that `id` already exists. A retry after a dropped response then can't duplicate anything. This is also worth doing for the online path, since it fixes the expense-without-splits gap above.

**The queue.**
- An IndexedDB store of `{ id, groupId, row, splits, receiptBlob?, createdAt, attempts, lastError }`.
- Adding an expense offline writes to the queue, adds a copy to `state` with a `pending: true` flag so it appears on the group page and in balances straight away, and shows a small "waiting to sync" mark on the row.
- Replay triggers: the browser's `online` event, the tab becoming visible, app start, and a timer with backoff (5s, 30s, 5min). Replay in creation order, one at a time.
- If the app is closed, items wait in IndexedDB. Where the browser supports Background Sync the service worker can replay, but it is not available on iOS, so the foreground triggers above are the dependable path.
- Order with live updates: replay the queue **before** reloading from the server, then reload. Otherwise a reload could briefly drop the pending row, then show it again.

**What can go wrong at replay, and what the user sees.**

| Case | Behaviour |
| --- | --- |
| Network error, timeout | Keep, retry later |
| Success, or `id` already exists | Remove from queue, clear the pending flag |
| Group archived meanwhile | Keep as "Couldn't add: the group was archived." Offer Discard, or Restore the group then retry |
| User left or was removed from the group | Same, offer Discard |
| A person in the split no longer exists | Same, offer Discard or Edit |
| Auth expired | Refresh the session; if that fails, stop and prompt sign-in. Never discard the queue |

Failed items stay visible (a banner on Home, the pending mark on the row) until the user acts. The queue never throws anything away on its own.

**Currencies.** An expense in another currency needs a rate. Offline, use the last rate cached for that pair (cache rates in IndexedDB too) or let the user type one, which the sheet already supports. Mark such entries "rate to check" so it's clear it wasn't the ECB rate for that date.

**Receipts.** Keep the blob in the queue entry and upload it at replay, before the expense insert, as today. Cap how many photos can wait (say 10 or 50 MB) and say so when full.

**Recurring expenses** are server-side and unaffected. Creating a schedule offline is out of scope.

## Out of scope for the first version

- **Edits and deletes offline.** They need conflict handling when someone else changed the same entry. Disable them offline.
- **Creating or joining groups, inviting, settling up (recording payments) offline.** Recording a payment is the one I would add next, since it has the same shape as an expense.
- **Offline sign-in.** The Supabase session already persists in `localStorage`; the only job is not to treat a failed token refresh as a sign-out when offline.
- **Merging offline edits from two devices.** Adds are safe because every entry has its own ID. Edits are not.

## Testing

- Pure queue logic (ordering, retry timing, outcome handling per the table above) as unit tests, like the rest of `src/lib/`.
- A Playwright run with `context.setOffline(true)`: open the app from cache, add an expense, go online, check it syncs once, check it doesn't double up on a forced retry.
- A manual pass on a real iPhone installed to the Home Screen, since iOS is the strictest about service workers and storage.

## Build order and size

1. `add_expense` function and use it online (small, and valuable by itself).
2. Layer 1, app shell cache (small to medium).
3. Layer 2, read cache and offline banner (medium).
4. Layer 3, queue with pending marks and failure handling (the bulk of the work).

## Decisions needed

- Is "add expense only" the right first cut, or is offline payments needed at the same time?
- Is storing a copy of the data on the device (unencrypted IndexedDB) acceptable? The alternative is not caching, which means no offline reading.
- Is a "Couldn't add" banner enough for failures, or do you want a dedicated "Waiting to sync" screen?
- Should the app shell cache include a "new version" prompt, or reload silently on next open?
